# ADR 0005 — Previews inside the element via an action signal

**Статус:** принято, 2026-10-19.

## Контекст

Меню нужно 4 превью (off/blur/beauty/blur-beauty), желательно с тем же
кадром и теми же настройками, что и видео. Если daemon создаст второй
набор моделей, это удвоит память/NPU и нарушит DRY. Если daemon будет
линковаться с C++-классом элемента, появится жёсткая связанность.

## Решение

Элемент хранит последний кадр (snapshot, копия ≤2 Гц) и предоставляет
**action signal** `generate-previews(dir)` с возвратом `a{ss}`. Обработчик
внутри элемента вызывает `PreviewGenerator` с тем же `EffectProcessor`,
что и видео, и пишет PNG в `/run/user/<uid>/npu-effects`.

Daemon вызывает signal через `g_signal_emit_by_name` и возвращает пути UI
по D-Bus. UI читает PNG и отдаёт их в DBusMenu как `icon-data`.

## Последствия

- Один экземпляр моделей; превью и видео используют одинаковую логику.
- Генерация превью синхронна и на время блокирует streaming (4 кадра
  640×360); поэтому она запускается при активации камеры, раз в 5 с и по
  кнопке «Обновить превью», а не на каждый кадр.
- Daemon не зависит от заголовков элемента; контракт — GStreamer/GObject.
- Snapshot — копия, а не живой буфер; нет гонок с GStreamer.

## Альтернативы

- Второй `EffectProcessor` в daemon: дублирование моделей и логики.
- Линковка daemon с элементом: связанность и конфликт GType при плагине.
- Генерация превью в UI: UI не имеет доступа к кадру и моделям.
